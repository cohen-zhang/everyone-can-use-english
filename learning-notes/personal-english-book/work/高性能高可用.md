## A. ZME 定时器 · 故障恢复问题（案例 1）

### 中文原文

研发今天发现了一个 ZME 的问题：

- **问题原因：** 在故障恢复的场景下，框架在处理定时器消息时，触发了一个 ZMI 的 bug，导致 ZMI 消息的滑窗被填满，备机 rejoin 失败。
- **复现方法：** ZME 在故障恢复前，设置多个定时器任务；故障恢复后，ZME 主启动成功，备机在 join 的阶段恢复之前的定时器，已到期的定时器被触发；同时由于同步主节点，新的消息注册新的定时器，在并发场景下会产生该问题。
- **修复影响场景：** ZME 定时器相关场景，可选择其一产生多个定时器任务；ZME 撮合配置一定延迟，保证产生定时任务。需测试：持续产生定时任务场景下的单个节点宕机、主备来回 rejoin、多节点宕机故障恢复。

### 英文改进稿（保留原意）

R&D discovered a **ZME** issue today.

- **Root cause:** During **fault recovery**, while the framework was processing **timer messages**, it hit a **ZMI** bug. The **ZMI message sliding window** filled up, and **standby rejoin** failed.
- **Repro steps:** Before ZME recovers from the fault, configure **multiple timer tasks**. After recovery, the **ZME primary** starts successfully. During the standby **join** phase, it restores the previous timers and **fires expired timers**. At the same time, it syncs with the primary and **registers new timers** for new messages. Under **concurrency**, this triggers the issue.
- **Fix impact / test scope:** ZME **timer-related** scenarios—pick one path to create **multiple timer tasks**. Add **matching config delay** on ZME so scheduled tasks keep firing. Test: **continuous scheduled tasks** with **single-node outage**, **primary–standby rejoin back and forth**, and **multi-node failure recovery**.

## F. 高可用场景 · 可复用句

*主备切换、rejoin、脑裂、滚动升级、灰度回滚、双活、混沌、RTO/RPO。*

| 场景 | 中文要点 | 英文 | 状态 |
| --- | --- | --- | --- |
| 主备切换检查 | 切主后核对复制延迟、读写路由与告警。 | After **failover**, verify **replication lag**, **read/write routing**, and that **alerts** are clean. | 已补 |
| rejoin 超时 | 备机 rejoin 超时，需查网络与滑窗。 | **Standby rejoin timed out**—please check the network path and whether the **sliding window** is full. | 已补 |
| 脑裂 | 怀疑脑裂，先隔离一侧再对齐数据。 | We may have a **split-brain**. **Fence** one side first, then **reconcile** data. | 已补 |
| 滚动升级 | 按节点滚动升级，观察集群健康再继续。 | Run a **rolling upgrade** node by node; proceed only when the cluster stays **healthy**. | 已补 |
| 灰度回滚 | 金丝雀异常，立刻回滚到上一版本。 | The **canary** looks bad—**roll back** to the previous version immediately. | 已补 |
| 双活 / 多活 | 双活要求两边都能接流量并处理冲突。 | **Active–active** means both sides take traffic and we must handle **conflict resolution**. | 已补 |
| 混沌工程 | 用混沌演练验证故障注入下的恢复。 | Run a **chaos drill** to validate recovery under **fault injection**. | 已补 |
| RTO / RPO | 本次演练 RTO 约 2 分钟，RPO 接近零。 | In this drill, **RTO** was about **two minutes** and **RPO** was near **zero**. | 已补 |

### F.1 主备切换检查清单（英文短句）

1. Confirm the new **primary** is elected and accepting writes. — 确认新主已选出并接受写。
2. Check **standby** is in sync / **rejoin** completed. — 确认备机同步或 rejoin 完成。
3. Validate **clients** reconnect without sticky old primary. — 确认客户端未粘在旧主上。
4. Watch **error rate**, **latency**, and **replication lag** for 15–30 minutes. — 观察错误率、时延与复制延迟 15–30 分钟。
5. Close the incident only after **post-failover** health is green. — 切主后健康全绿再结案。

## G. 性能与压测 · 可复用句

*TPS/QPS 口径、P99、阶梯压测、soak、瓶颈定位、容量报告、环境差异。*

| 场景 | 中文要点 | 英文 | 状态 |
| --- | --- | --- | --- |
| TPS / QPS 口径 | 先对齐口径：TPS 含写，QPS 偏读。 | Align on metrics first: **TPS** covers writes; **QPS** is mostly reads. | 已补 |
| P99 时延 | 均值正常，但 P99 已经超 SLO。 | Average latency looks fine, but **P99** already **breaches the SLO**. | 已补 |
| 阶梯压测 | 按 1k→2k→4k TPS 阶梯加压，找拐点。 | Run a **stepped load**: 1k → 2k → 4k TPS to find the **inflection point**. | 已补 |
| 长时间稳定性 | 做 4 小时 soak，盯内存与 GC。 | Run a **4-hour soak test**; watch **memory** and **GC** the whole time. | 已补 |
| 资源瓶颈定位 | 当前像 CPU 打满，其次是 GC 停顿。 | It looks like a **CPU bottleneck**, with **GC pauses** as a secondary factor. | 已补 |
| 容量评估 | 按峰值 × 1.5 做容量评估并留余量。 | Do **capacity planning** at **peak × 1.5** and keep headroom. | 已补 |
| 压测环境差异 | 压测机配置弱于生产，结论需打折。 | The **load-test env** is weaker than prod—treat results with a **discount**. | 已补 |
| Vx.x.x 基准 #2 | （占位）吞吐量达顶后错误率抬头。 | Once **throughput saturates**, the **error rate** starts to climb. | 已补·待用真实数据替换 |

### H.3 发版前 HA 回归 checklist（英文）

- [ ] **Single-node outage** — primary kill; standby takes over within RTO.
- [ ] **Primary–standby switchover** — manual + automatic paths.
- [ ] **Standby rejoin** — after recovery, rejoin succeeds; no split-brain.
- [ ] **Multi-node failure recovery** — two nodes down, cluster still serves (or fails safely).
- [ ] **Rolling upgrade** — one node at a time; no write loss.
- [ ] **Canary + rollback** — canary unhealthy → rollback completes cleanly.
- [ ] **Timer / matching delay** scenarios still pass under continuous load (if applicable).
- [ ] Alerts, dashboards, and **post-failover** metrics reviewed for 15+ minutes.
